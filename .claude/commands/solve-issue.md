# Issue実装ワークフロー

対象Issue番号: `$1`

このセッションが**指揮官**である。指揮官は計画・レビュー・コミット・マージを担当し、
**コードの編集は必ずSonnetのサブエージェントに委譲する**（指揮官が直接コードを書いてはならない）。

## 0. 前提確認

1. Issue番号を4桁ゼロ埋めに正規化する（`6` → `0006`）。
2. `docs/issue/0006-*.md` 形式のファイルを探し、**全文を読む**。見つからなければ中断して報告する。
3. Issueの `依存` 欄を確認する。未完了の依存があれば**実装せず**、その旨を報告して中断する。
4. `git status` が clean であることを確認する。未コミットの変更があれば中断して報告する
   （勝手に stash/commit/破棄をしてはならない）。
5. `docs/design.md` の 13.3（禁止事項）と、Issueが `関連` で挙げている節を読む。

## 1. ブランチ作成

main から生やす。

```
git switch main
git switch -c feature/0006-<Issueファイル名のスラグ>
```

（例: `docs/issue/0006-pin-toggle.md` → `feature/0006-pin-toggle`）

## 2. 実装計画

Issueの「やること」「完了条件」を、**1コミットに収まる粒度のタスク**に分解する。

- Issueに書かれていることだけを分解する。良かれと思った改善・リファクタリング・
  周辺コードの整理は**タスクに含めない**。
- 各タスクについて「触るファイル」「変更内容」「完了条件のどれに対応するか」を明示する。
- 計画をユーザーに提示する（承認待ちは不要。そのまま実装に進む）。

## 3. 実装（Sonnetへ委譲）

タスクを1つずつ、順番に処理する。1タスクごとに以下を繰り返す。

1. `Agent` ツールで `subagent_type: minimal-code-editor`（Sonnet）を呼び、
   **そのタスク1つだけ**を依頼する。プロンプトには必ず以下を含める。
   - Issueの該当箇所の抜粋（サブエージェントはIssue全文を持っていない前提で書く）
   - 触ってよいファイルと、変更してほしい内容
   - 「指示された変更以外は一切行わないこと。リファクタリング・整形・コメント追加・
     不要なテスト追加をしないこと」
   - 「`git commit` / `git switch` / `git branch` は実行しないこと。コミットは指揮官が行う」
2. サブエージェントの完了後、指揮官が `git diff` を読んでレビューする。
   - Issueが話題にしていない変更が混入していたら、その部分を戻す（サブエージェントに
     差し戻す、または最小限の巻き戻しを行う）。
   - 意図した変更が入っていなければ、具体的に指摘して同じエージェントに差し戻す。
3. ビルド・テストを通す。`make build` と `swift test`。失敗したら修正を
   サブエージェントに依頼する（指揮官が直接直さない）。
4. **コミットする**。1タスク=1コミット。Conventional Commits 形式・日本語の件名とする
   （例: `feat: ピン留めのトグル操作を追加`）。本文に `Issue: 0006` を含める。
   コミットメッセージ作成には `common:commit-msg` スキルを使う。

タスクをまとめて実装してから一括コミットするのは禁止。細かく積む。

## 4. 指揮官による最終確認

全タスク完了後、指揮官が以下をすべて確認する。

- `make build` が成功する
- `swift test` が全て通る
- `git diff main...HEAD` を読み、Issueの**完了条件を1つずつ**満たしているか照合する
- 同じ差分に、Issueに書かれていない変更が**含まれていない**ことを確認する
- `docs/design.md` 13.3 の禁止事項に触れていないことを確認する
- 検索性能に影響する変更を入れた場合は、性能ゲート（60,000件・リリースビルドで16ms以内）を
  再計測する

不足・過剰があれば §3 に戻る。

確認が通ったら、Issueファイルの `状態` 行のみを `完了` に更新してコミットする
（`docs: 0006 を完了に更新`）。それ以外の記述は書き換えない。
なお設計判断をIssueの記載から変えた場合は、`docs/design.md` にも反映する。

## 5. mainへマージ

```
git switch main
git merge --no-ff feature/0006-<スラグ>
```

マージ後、`make build` と `swift test` をもう一度実行して緑であることを確認する。
featureブランチは削除しない（残しておく）。

## 6. アプリ再起動

マージ後、**必ず** 以下を実行してアプリをビルドし直し、再起動する（省略禁止）。

```
scripts/restart.sh
```

スクリプトが失敗した場合は、原因を調査して修正し、再度実行して成功させる。

## 7. 報告

以下を簡潔に報告する。

- 実装したIssueの番号とタイトル
- 積んだコミットの一覧（`git log --oneline main` の該当範囲）
- 完了条件それぞれの充足状況
- 実機確認が必要な項目（キー操作の動作など、自動テストで担保できないもの）
